The problem statement

Uniform grids waste memory on places that don't matter yet

An autonomous ground vehicle sees the world through LiDAR: roughly 120,000 3D points, ten times a second. The standard representation is a uniform grid — the same tiny cell size from the robot's bumper out to 100 metres.

That uniformity is the waste. A cell 90 metres away holds one or two laser returns at most; it cannot support fine detail, yet it consumes the same memory as a cell at the robot's feet. On embedded hardware, that gap is the difference between a map that fits and one that doesn't.

The problem statement asks for an adaptive, variable-resolution 2.5D map: full detail near the vehicle where driving decisions happen, progressively coarser at range — without losing safety-critical information, and with the memory savings demonstrated, not claimed.

Our approach

Foveation: resolution that follows relevance

The human eye solves the same problem. The fovea is packed with receptors; the periphery is coarse. FoveaMap applies that layout to the robot's map: four concentric rings, each doubling the cell size of the one before.

RingDistanceCell sizeWhy this size
12.5 – 10 m5 cmKerbs, potholes, small obstacles — the braking-decision zone
210 – 25 m10 cmPath-planning horizon

Three design decisions carry the whole project

1. Exactly-nested rings, lossless merging

Cell sizes are powers of two of 5 cm, so four small cells always tile one larger cell exactly. Merging fine into coarse runs the identical arithmetic as building coarse directly — results are bit-identical, proven by automated test. Resolution changes lose nothing.

2. Full statistics, never a majority vote

Per cell: lowest, highest, mean, and variance of height, plus a count of every class seen. A cell with 99 road points and 1 pedestrian must not vote the pedestrian out of existence. Height variance is what separates flat road from a kerb; lowest height is where a pothole lives.

3. Proven network, no random fallback

SalsaNext with published pretrained weights labels each point, simplified to three driving-relevant classes. If weights are missing the pipeline stops — it never silently falls back to a random model.

The same pipeline, no jargon

Five steps, every term explained

Step 1 — 3D data from KITTI

LiDAR is a spinning laser that measures distances, producing a point cloud — roughly 120,000 dots in 3D space, ten times a second. KITTI / SemanticKITTI is a public dataset of real car drives where every point is hand-labelled. Poses record where the car was at each moment; calibration is the math converting between the sensor's coordinate frame and the car's.

Step 2 — Preprocess: spherical projection

The 3D points are wrapped onto a 2D image (64×2048 pixels) using angles, like flattening a globe into a map. Range is the distance from the sensor, stored per pixel. Collision handling: when two points land on the same pixel, keep the closer one — the safe choice.

Step 3 — Deep learning: SalsaNext

SalsaNext is a published semantic segmentation network: it labels every pixel with a class (ground / static obstacle / dynamic) rather than drawing boxes around objects. Inference means running the trained network. fp16 means doing the math with 16-bit numbers instead of 32-bit — half the precision, nearly twice the speed (50.6 ms → 26.2 ms on a Tesla T4). Latency is time per frame; the budget is 40 ms.

Step 4 — The foveated grid engine (our contribution)

Foveated comes from the fovea, the sharp centre of the human eye: high detail near, coarse far. Labelled points are projected onto a top-down grid of concentric rings, each with its own cell size — 5 cm near the car, 40 cm at 100 m. A 2.5D elevation grid is a 2D map where each cell also stores height statistics. Welford accumulation updates a cell's mean and variance one point at a time, numerically stable, without storing the points themselves.

Step 5 — Display and proof

The grid renders live in the demo dashboard with memory and FPS meters: 3.30 MB per sweep instead of the raw cloud. Recall is the fraction of real obstacle cells the map kept (92–97% for us; a flat 2D grid loses ~14%). Baselines are the simple alternatives we compare against: a uniform 5 cm voxel grid and a flat 2D occupancy grid. Provenance means every result file records the exact git commit, hardware, and configuration that produced it; reproducibility means a stranger can rerun it all and land within 2% of every number.

What is a Pareto curve? With two competing goals — use less memory, miss fewer obstacles — you cannot maximise both. A Pareto curve plots memory against recall for many map configurations and traces the best possible trade-offs: the points where improving one goal must hurt the other. Our claim, and the project's primary deliverable, is that the foveated grid sits above the uniform-grid baselines on this curve — same safety, a fraction of the memory.

The demo dashboard shows all three side by side on the same real scan. Here is what each one is, and what it costs — every figure below is measured, not estimated.

The one-line version of each

3D: sees everything, but memory grows forever and it answers no questions by itself. 2D: cheap, but forgetful — it throws away what and how tall, and the measured price is about 15 recall points in every distance band. 2.5D foveated: bounded memory, 92–97% recall, and the only one of the three that can answer "is this a kerb, a pothole, or a person?" at all.

The honest sentence for a jury

"We do not store the least — we store the right things in the right places, at a memory size that never grows."

What to say when asked to show it

Open the dashboard

Run python -m src.main viz --seq 00. Point at the map and say: "Inner ring — 5 cm cells, that's where braking decisions live. Each outer ring doubles the cell size. The memory goes down; the map still covers 100 m."

Show the memory number

The HUD always shows live MB. Say: "3–4 MB per sweep for the foveated grid. A flat 5 cm grid over 100 m would be roughly 10× that. That gap is what the Pareto curve measures."

If they ask about the colours

■ Blue = road/ground.   ■ Amber = static obstacle (walls, parked cars).   ■ Red = dynamic (vehicles, people). Same palette everywhere — debug views, analytics, final demo.

If they ask "why not just zoom in on the important part?"

The robot doesn't know what's important until it sees it. The foveated grid commits memory to distance, not content — which is predictable and provable. Zoom-on-demand requires a prior; rings don't.

If the demo machine is slow

Replay a recorded run: python -m src.main viz --seq 00 --save runs/viz.rrd, then open the .rrd locally. The cached-mode banner appears automatically — never claim live FPS from a replay.

Closing line

"Every number on this screen traces to a provenance-stamped run in runs/. Hardware, git commit, config — all recorded. Anyone can regenerate it."

Preparation

Questions a jury will ask, and our answers

What is actually novel here?

Not variable resolution by itself — octrees and multi-resolution maps exist. The contribution is the combination: exactly-nested rings with provably lossless aggregation, full per-cell statistics that preserve safety-critical minorities (the one pedestrian among 99 road points), and a benchmark methodology where memory and recall share a fixed reference denominator so the comparison cannot be gamed.

How do we explain it in ten seconds?

"Think of high-poly versus low-poly models in a 3D game: full detail close to the camera, simplified geometry far away, so everything fits in memory. Our grid does that for LiDAR perception — 5 cm cells near the vehicle where braking decisions happen, 40 cm far away. The difference from a game: our coarse cells are not just blockier — each one still carries minimum height, variance, and a full class histogram, so a pothole, a kerb, or a pedestrian stays represented in the statistics even where the grid is coarse. Measured on the validation sequence, recall inside 10 m stays within 1% of the full-resolution reference."

Why rings and not an octree?

Relevance in ground-vehicle driving is a function of distance from the vehicle, which rings encode directly and cheaply. An octree adapts to point density instead — it spends detail wherever returns are dense, which is not the same thing as where decisions are made — and pays pointer-chasing costs on an embedded target. Rings also make the memory model predictable, which is the property being sold.

Why is merging cells "lossless"? Averages lose information.

Each cell stores count, mean, and the running sum of squared deviations (Welford's method). Two cells combine into exactly the statistics the merged point set would have produced — mathematically, not approximately. Naively averaging two variances is wrong and looks right; our tests enforce the correct combination bit-for-bit.

Why should we trust your numbers?

They are stratified by distance band, scored on the standard held-out validation sequence, against human-labeled ground truth, from a provenance-stamped run that records hardware, commit, and configuration. The pipeline refuses to produce benchmark numbers from cached or CPU inference without a persistent on-screen banner. Every figure in this document traces to a file in runs/.

What about potholes and drop-offs?

Negative obstacles are emitted as candidates with confidence, never hard detections: ground plane fitted per region, missing returns flagged only after occlusion by a classified obstacle is ruled out. When our ground-truth count for real potholes came back unreliable (197,828 — too large, caused by map misalignment), we said so and scheduled manual verification rather than scoring against noise.

What runs on the GPU and what doesn't?

Only Module B (SalsaNext inference) needs a GPU. Projection, the grid engine, analytics, and benchmark aggregation are pure CPU — which is why nine of ten stages progressed on a 4-core VM before any GPU was provisioned.

If the demo machine is slow on finale day?

Official FPS figures cite the measured GPU (T4 class); the fallback ladder — FP16, narrower projection, pruning — is decided in stage 5, not improvised on stage. The demo can also replay a recorded run, in which case the cached-mode banner is visible by design: we never present replay as live throughput.

How does this generalise beyond KITTI?

The ring table is a config file, not hard-coded geometry. Any sensor with a known range and a calibration file drops in: change configs/pipeline.yaml and the ring table, re-run the validation command, and the assertions enforce the same plausibility checks. The grid engine, analytics, and benchmark harness are sensor-agnostic once the ring table passes.
